# SnapFit 포토북 제작 운영

현재 기준은 **2026-10-15**이다. 신규 고객 주문은 [앱 PDF와 Supabase 자동 발주](vendors/supabase-app-pdf-orders-2026-10-15.md)를 따른다. [포트원 주문 구현과 운영 설정](vendors/portone-checkout-setup-2026-10-13.md), [자동 제작 작업](vendors/print-fulfillment-worker-2026-10-14.md), [업체 개발 주문과 최신 회신](vendors/redprinting/development-tests-2026-10-08.md)을 따른다. 9월의 웹 조사와 수동 제작 기록은 이력으로 보존한다.

## 현재 범위

레드프린팅 PHBKMYB의 공식 재단 규격 5종(200×150, 200×200, 250×200, 250×250, 300×300mm)을 지원한다. 각 크기에 소프트커버 또는 사진을 인쇄하는 하드커버 이미지랩을 선택한다. 소프트커버는 아트지 300g, 하드커버는 스노우 180g이며 표지는 무광 코팅, 내지는 유광 캐논전용지 285g 기준이다. 내지 20–80페이지를 2페이지 단위로 만든다. 고객 주문에 결제 전 앱 PDF 생성·비공개 업로드·서버 검수, PortOne V2 결제 확인, Supabase의 레드프린팅 API 접수·입금 완료·상태 조회를 연결했다. 실제 판매는 현재 비활성이다.

현재 PortOne에는 토스페이먼츠 TEST 채널만 설정되어 있다. 고객은 앨범에서 제작 미리보기와 예정 가격을 확인하고 검수용 PDF를 만들 수 있지만, 사업자·운영 PG·인쇄업체 운영 계약/키·실물 샘플·확정 원가·Supabase 자동 실행의 운영 조건이 확인되기 전에는 실제 결제를 열지 않는다. 운영 승인 후에는 고객이 업체 사이트를 방문하거나 관리자가 매번 PDF를 올릴 필요 없이 같은 고정 주문이 자동 처리된다. 과거 수동 주문은 기존 처리 경로를 유지한다.

## 고객 주문과 돈의 흐름

고객 화면은 **앨범 검수 → 배송지 → 최종 금액·주문 확인 → 앱 PDF 생성·업로드·서버 검수 → 포트원 결제창 → 서버의 결제 확인 → 주문 완료·진행 조회** 순서다. 결제 전 파일 준비는 앱을 열어둔 동안 수행한다. 검수가 끝난 동일한 파일에 실제 운영 결제 영수증이 확인되면 Supabase Cron이 레드프린팅 접수 → 파일 분석 → 입금 완료 처리 → 제작 → 송장 조회를 진행한다. 결제 후 앱을 꺼도 계속되며 관리자 승인 버튼이나 별도 PDF 생성 서버가 필요하지 않다. 비용 변동·불확정 접수·결제 취소·파일 수정 요청은 보류하고 운영자에게 상태를 표시한다.

돈은 두 경로로 움직인다.

| 경로 | 처리 |
| --- | --- |
| 고객 → 계약한 PG → 스냅핏 정산 계좌 | 포트원으로 결제를 연결하고 PG가 계약한 주기에 수수료 등을 반영해 정산한다. 결제 승인이 즉시 계좌 입금을 의미하지 않는다. |
| 스냅핏 → 레드프린팅 예치금 → 주문별 제작비 | 예치금을 먼저 충전하고 API 주문의 입금 완료 단계에서 제작비를 차감한다. 고객 카드 결제금이 업체로 직접 전달되지 않는다. |

예를 들어 소프트커버 20쪽 예정가 49,900원에 고객이 결제하더라도, 확인된 제작비 21,230원+배송 3,500원=24,730원은 미리 준비한 제작 자금으로 지급해야 한다. PG 정산을 기다리지 않고 발주하려면 정산 전 주문을 처리할 만큼 예치금이 필요하다. 실제 잔액·정산 주기·정산 계좌는 아직 확인하지 않았고, 예치금을 충전하거나 자동 충전 서비스를 신청하지 않았다. [PG 정산 구조](https://docs.tosspayments.com/resources/glossary/settlement)

사업자등록과 계좌·PG/제작 계약은 운영자가 완료해야 한다. 운영 키를 서버 비밀 설정에 넣고 확정 사양/가격을 승인하며, 이미 설정한 Supabase 자동 실행의 운영 상태를 확인한 다음 실결제·업체 접수·실물 샘플의 전체 흐름을 검증한다. 앱의 주문 흐름 구현과 실제 계약/잔액/품질 확인은 별개다.

PC 관리자 **인쇄 연동 → 실제 판매 준비**에서 설정 조회와 담당별 남은 조건을 확인한다. 개발 테스트 점검과 실제 판매 준비를 구분하며, 이 화면은 승인·금액·예치금·판매 개방을 변경하지 않는다. 신규 경로의 자동 실행은 [앱 PDF와 Supabase 설정](vendors/supabase-app-pdf-orders-2026-10-15.md)을 따른다. 별도 Linux/Railway 설치안은 과거 준비 기록이며 이번 경로에서는 사용하지 않는다. 유료 서비스와 요금제를 추가하지 않았다.

## 일반 사용자 주문 화면과 중단 복구

일반 사용자 동선은 앨범 완성 → 인쇄 미리보기 → 배송지 입력 → 주문 내용 확인 → 파일 준비와 결제 → 주문 진행 상황 → 마이의 주문 내역이다. 실제 판매가 닫혀 있어도 배송지와 주문 내용을 화면에서 확인할 수 있지만, 결제 버튼은 준비 중으로 표시되고 결제창·실주문·발주는 생성하지 않는다. 관리자 TEST 화면은 이 경로와 별도다.

파일 준비가 중단되면 같은 결제 준비 기록을 먼저 조회한다. 원본 업로드 증거가 모두 확인된 묶음은 PDF를 다시 만들지 않고 기존 파일 검수를 이어간다. 부분 업로드를 다른 파일로 덮거나 새 결제를 자동 생성하지 않는다. 고정된 주문의 배송지를 바꾸려면 기존 준비 주문의 취소 완료를 확인한 뒤 다시 준비한다. 결제창 이후에는 원래 결제번호의 서버 조회로만 결과를 확인한다.

주문 내역은 결제 대기·자동 발주 대기·제작사 접수·파일 확인·제작·배송·완료를 구분하며 상세를 열어 둔 상태와 앱 복귀 때 갱신한다. 조회에 실패하면 마지막 확인 상태와 오류 안내를 함께 유지한다. 취소·환불 요청 접수를 실제 취소·환불 완료로 표시하지 않는다. 다른 기기의 기존 주문 조회는 결제창을 재실행하지 않는다. TEST 기록은 고객 목록에서 제외하고, 계정이나 실제 인증 세션이 바뀌면 이전 고객의 배송정보를 즉시 가린다.

2026-10-15 보완분은 [검증 기록](../../output/customer-print-order-2026-10-15/backend-tests.json)과 [실결제 잠금 확인](../../output/customer-print-order-2026-10-15/live-sales-closed-after.json)을 따른다. 관리자 소유 80페이지의 실제 TEST/DEV 자동 처리 증거는 [별도 기록](vendors/admin-test-checkout-e2e-2026-10-15.md)에 있으며, 일반 사용자 LIVE 결제를 실행했다는 뜻은 아니다.

## 고객 미리보기와 PDF

1. 앨범을 저장한 뒤 ‘인화 주문’ 안내에서 제작 미리보기를 연다.
2. 서버가 실제 저장된 내지를 세고 최소 20페이지·짝수로 올린다. 80페이지를 넘으면 진행할 수 없다. 추가 빈 페이지는 뒤에 붙는다.
3. 새 앨범은 선택한 물리 규격을 `cover_layers_json.printProduct`로 저장하며 미리보기·내지·표지가 모두 그 규격을 사용한다. 같은 정사각형이어도 20·25·30cm가 구분되며 상품 ID의 `_SOFT`/`_HARD`로 표지 종류까지 유지된다. 일반·AI 생성에서 크기와 표지 종류를 따로 선택하고, 표지 종류만 변경하면 기존 사진과 문구 위치를 유지한다. 과거 상품 정보가 없는 정사각형은 200×200, 가로 4:3은 200×150mm로 안내한다. 기존 세로형은 열기·편집을 보존하고 새 실물 제작 미리보기는 지원하지 않는다. 과거 결제된 V1 주문은 원래 200×200mm 계약을 유지한다.
4. 원본 사진과 글꼴을 확인한다. 실제 배치 크기에서 사진이 150ppi 미만이면 중단하고 300ppi 미만이면 화질 안내를 표시한다. 원본 누락이나 렌더링 오류를 빈 이미지로 대체하지 않는다.
5. 300dpi 표지 PDF 1페이지와 내지 PDF를 만든다. 기존 Flutter 레이어 렌더러로 글꼴·크롭·회전·프레임·스티커를 합성한다. JPEG 품질 95와 내장 sRGB 프로파일을 사용한다.

현재 출력은 PDF 1.4 sRGB이다. PDF/X 또는 CMYK 인증 파일로 표시하지 않는다. 업체는 인화지 상품의 RGB 사용과 별도 권장 프로파일 없음, 내지 낱쪽을 순서대로 넣은 PDF 한 파일 제출을 안내했다. 이는 현재 생성기의 sRGB 프로파일·PDF 1.4 형식이나 특정 출력 파일의 승인을 뜻하지 않는다. 별도 면지 규칙과 색상·재단·제본 실물 결과는 계속 확인한다. 기본 책등 두께는 소프트커버 `0.52+0.67×(쪽/2)`, 하드커버 `2.40+0.67×(쪽/2)`로 서로 다르다. 각 종류의 공식20·22·80페이지 도면 측정에 맞춘 추정식이므로 실제 주문 면수 도면과 대조해야 한다. 하드커버는 내지보다 가로·세로6mm 큰 보드와 사방20mm 감싸기 여유를 사용한다. 내지 재단 크기와5mm 여유는 선택 크기에 따라 유지한다.

## 80페이지와 큰 PDF의 전송

무료 Storage의 50MB 제한은 저장 객체 한 개에 적용된다. 페이지 수는 기존대로 내지 20–80페이지이며, PDF가 50MB를 넘었다는 이유로 80페이지 주문을 막지 않도록 전송 경로를 확장했다. 50MB 이하 파일은 기존 방식으로, 큰 파일은 앱이 같은 원본 바이트를 최대 16MB 조각으로 나눠 비공개 저장소에 올린다. JPEG 품질 95, 300dpi, sRGB, PDF 1.4와 사진·글 배치는 그대로 유지한다. 추가 이미지 압축이나 페이지 축소를 자동 적용하지 않는다.

표지 한도는 150MB, 내지 한도는 500MB이며 각 조각의 실제 길이·SHA와 전체 원본 SHA, 페이지·규격·재단·색상 프로파일 검사가 모두 통과해야 결제창을 연다. 업체에는 조각 목록이 아닌 표지 PDF 한 개·내지 PDF 한 개의 만료 서명 URL을 전달한다. Supabase가 다운로드할 때 원래 순서로 이어 보내므로 업체가 받는 파일의 SHA는 앱이 만든 원본과 같다. 기존 결제 확인·중복 발주 방지·취소 보류·예치금 조건은 유지한다.

추가 유료 서버나 요금제는 사용하지 않는다. 조각도 무료 저장 공간·전송량·호출 수를 사용하므로 소량 개발 시험은 현재 무료 제공량 안에서 진행하고, 실제 운영 전 사용량과 미결제 파일 정리 상태를 확인한다. 코드·실제 80페이지 원본·결제 전 차단과 단일 PDF 전달의 검증 범위 및 원격 적용 상태는 [대용량 원본 PDF 전송 기록](vendors/large-original-pdf-transport-2026-10-15.md)을 따른다.

## 과거 수동 주문의 관리자 제작 순서

아래 수동 처리는 과거 주문에만 적용한다. 신규 `PORTONE_V2_V1` 주문은 고정된 결제·사양·작업 기록을 사용하며 관리자 상세의 수동 접수·입금·출고 입력으로 바꾸지 않는다. 신규 자동 처리 설정은 [앱 PDF와 Supabase 문서](vendors/supabase-app-pdf-orders-2026-10-15.md)를 따른다.

1. **제작 자료 준비:** 검증된 결제 주문의 고정 스냅샷으로 생성한다. 현재 앨범의 이후 편집은 해당 주문에 반영하지 않는다.
2. **도면 대조:** 정확한 상품·페이지 수로 업체가 제공한 표지 도면을 확인한다. 업체는 별도 맞춤 도면을 제공하지 않으므로 제공 도면의 규격을 따른다. 책등 두께가 다르면 근거와 함께 수정한 뒤 PDF를 다시 생성한다. 관리 화면은 서버의 현재 도면을 자동으로 채운다. 기본 하드커버 도면은 책등 폭 변경에 맞춰 앞표지 위치와 전체 폭을 조정하며, 선택 상품의 제공 도면에서 보드/여유까지 달라지면 ‘세부 도면 조정’으로 일치시킨다. 임의 도면을 제작사가 수용한 것으로 간주하지 않는다.
3. **자체 파일 검수:** 표지·내지 PDF를 열어 크기, 재단 여유, 낱쪽 페이지 순서, 사진과 문구 누락을 확인한다. 업체는 주문 전 사전 검수를 제공하지 않는다. SnapFit 운영자가 제공 도면과 PDF를 대조하고 실물 샘플 결과를 검수 기록에 남긴다. 파일 생성이나 자체 검수 완료만으로 제작 중 상태가 되지 않는다.
4. **발주 전 비용 확인:** 업체는 별도 견적을 제공하지 않는다. 실제 선택 옵션의 주문·결제 화면에 청구되는 제작비와 배송비, 필요한 포장비를 넣어 예상 잔여 금액을 확인한다. 운영자 경유 배송이면 택배 두 번과 재포장 비용을 포함한다. 10,000원 미만이면 업체 결제를 진행하지 않는다.
5. **수동 주문:** 레드프린팅에서 표지와 순서대로 된 낱쪽 내지 PDF를 각각 업로드한다. 배송 주소마다 업체 주문을 따로 생성한다. 고객 직배송 시 보내는 고객 정보의 `주문자(발송자명)변경`을 선택하고, 사용자가 지정한 한글 발송자명 `스냅핏`을 입력·확인한다. 별도 동봉물 없음은 회신으로 확인했지만 OPP 포장에는 주문번호 스티커가 붙는다. 로고나 표식이 없는 포장으로 안내하지 않는다. 배송 방식에 필요한 확인값과 근거를 기록하고, 운영자 수령을 선택한 경우 운영자 주소를 고객 주소와 혼동하지 않는다. 주문 버튼 아래 예상 출고일과 파일 문제 문자 안내를 받을 고객 연락처도 확인한다.
6. **발주 기록:** 실제 업체 주문번호, 영수증 기준 비용, 배송 방식과 확인 근거를 기록한다. 예시 주문번호나 임의 번호로 접수를 표시하지 않는다.
7. **접수 확인:** 업체 주문 화면의 실제 접수·제작 상태를 확인한 뒤 ‘제작사 접수 확인’을 기록한다. 업체 사전 검수 확인서를 기다리는 단계가 아니다. 주문번호 저장만으로 접수를 자동 확정하지 않는다. 파일 문제 문자가 오면 내용을 처리하고 실제 주문 상태를 다시 확인한다. 접수 확인을 기록할 때 앱 주문이 제작 중으로 바뀐다.
8. **배송:** 약 5–6영업일에 택배 운송기간이 추가된다는 안내와 주문별 예상 출고일을 기준으로 고객에게 예상 일정을 알린다. 확정 완료일·도착일을 보장하지 않는다. 고객에게 보내는 최종 택배사·운송장을 기록하고 실제 배송 완료를 확인한다.

파일 상태: `AWAITING_RENDER → RENDERING → REVIEW_REQUIRED → READY → SUBMITTED → ACCEPTED`. 업체 접수 이후에는 발주번호·제작 파일·비용을 덮어쓸 수 없다. 수정이나 재제작은 별도 운영 처리가 필요하다.

## 일반 주문 화면의 제한된 TEST 경로 (2026-10-15)

일반 배송지·주문 확인 화면에서도 개발 검증을 진행할 수 있도록 연결했다. 서버가 현재 관리자 계정과 앨범 소유권을 확인하고, 검토한 동일한 앨범의 **300×300mm 하드커버·내지 80페이지·159,900원 TEST** 구성을 허용한 경우에만 열린다. 일반 사용자의 기본 결제 경로와 실제 판매는 계속 닫혀 있다. 이 기능은 대중에게 TEST 결제를 개방하거나 일반 고객의 운영 결제를 승인하는 기능이 아니다.

일반 배송지 입력 → 주문 내용 확인 → 기존의 엄격한 개발용 PDF 생성·업로드·검수 → 지정된 포트원 TEST 채널 → Supabase Cron의 실제 TEST 영수증 확인 → 레드프린팅 개발 발주 → 주문 내역의 별도 TEST 목록·상세 순서다. SDK 콜백만으로 결제 완료를 표시하지 않고, 콜백에서 결제 확인이나 발주를 직접 실행하지 않는다. 기존 관리자 테스트와 일반 화면 테스트의 복구 저장소를 분리하며 같은 테스트의 결제번호·주문번호는 유지한다. 계정 변경 시 이전 배송정보를 즉시 숨긴다.

일반 화면에서 새 주문 `ordp_85e8ce97-1d30-41ee-892b-4c43ee5546f3`으로 실제 TEST 승인·개발 발주·재실행 후 주문내역 확인을 완료했다. 기존 관리자 테스트 주문을 재사용하지 않았다. 내지 **80페이지·100,423,186바이트·7조각**의 PDF를 업로드하고 전체 검수 `READY`를 확인했으며, 포트원 영수증은 **159,900원·PAID·isTest=true**이다. [실행 검증 기록](../../output/customer-test-checkout-e2e-2026-10-15/verification.md)과 [최종 증거](../../output/customer-test-checkout-e2e-2026-10-15/finalresult.json)를 따른다.

2026-10-15 한국시간 **15:36:32 TEST 승인 → 15:38:01 서버 영수증 검증 → 15:39:09 모든 앱 탭 종료 → 15:40:04 업체 전송 시도 기록 → 15:44:02 파일 분석 완료(`file_process_yn=Y`, `FILE_CHECKED`, 작업 `DONE`) → 15:47:15 앱 재실행** 순서를 확인했다. PG 결제 검증은 앱 종료 전에 완료됐다. 이번 실행은 이후 업체 자동 발주와 파일 분석이 앱이 닫힌 동안 진행된 것을 입증하며, PG 검증까지 앱 종료 후 수행됐다는 뜻은 아니다. 전송 시각은 시도 기록이고, 접수·분석 완료는 이후 업체 상태 조회로 확인했다. 재실행한 일반 주문내역의 별도 TEST 상세에서 같은 주문번호와 4단계 완료 상태를 서버 조회로 복원했다.

실제 판매의 `enabled`, `businessReady`, `portoneLiveReady`, `redprintingLiveReady`는 모두 `false`를 유지하며 실거래 고객 주문과 운영 결제 준비는 각각 0건이다. 실제 카드 청구·예치금 차감·책 제작·배송은 진행하지 않았다. 웹에서 PDF 생성에 약 12분이 걸렸고, 회색으로 남은 TEST 결제 iframe을 한 번 수동으로 새로고침해야 했다. 업체 원본 코드 `PGS_05` 주의 표시는 숨기지 않고 보존한다. 정기 실행 시각과 해당 주문 상태를 대조한 증거이며 개별 HTTP 요청과 주문을 직접 잇는 감사 식별자는 없다.
